# 首頁功能表區改造規劃

> 對應 [`V2_PLAN.md`](V2_PLAN.md) §4.1「功能density」，但範圍限定在首頁清單上方那一區。
> 現況是用 [`e2e/`](../e2e/) 的 harness 實際截圖得到的（`_shots.spec.ts`），不是讀程式碼推測的——版面問題只有在真的畫出來時才看得見。

## 1. 現況

桌機 1440px 下，清單上方擠了 **8 顆按鈕＋1 個搜尋框**，下面再接一張有 3 個欄位的篩選卡片：

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ makeslide  [🔍 跨所有簡報搜尋…]  ┌登┐┌設┐┌匯入┐┌匯出全┐ [⬇上傳PDF][貼上TXT][空白簡報] │
│                                 │出││定││ZIP ││部 ZIP│           [YouTube 匯入] │
│                                 └─┘└─┘└───┘└────┘                            │
├──────────────────────────────────────────────────────────────────────────────┤
│ ┌──────────────────────────────────────────────────────────────────────────┐ │
│ │ 顯示類別 [全部類別▾]   標題篩選 [輸入關鍵字…]   排序方式 [標題 A-Z▾]   [▦][≡] │ │
│ │ 顯示 4 / 4 份簡報                                                          │ │
│ │ 共 4 份簡報 · 4 頁 · 播放 0 次                                             │ │
│ │ [☆ 我的最愛] [全選]                                                        │ │
│ └──────────────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 1.1 診斷

| # | 問題 | 證據 |
|---|---|---|
| D1 | **空間已經不夠** | 「登出」「設定」「匯入 ZIP」「匯出全部 ZIP」四顆在 1440px 下都**折成兩行**；「YouTube 匯入」被擠到第二列 |
| D2 | **沒有視覺層級** | 同一列出現 5 種樣式：白框、深色實心、紫色實心、淺綠框、灰底 chip。哪個是主要動作看不出來 |
| D3 | **罕用／破壞性動作與高頻動作同級** | 「匯出全部 ZIP」（會打包整個帳號的簡報）和「上傳 PDF」一樣顯眼 |
| D4 | **職能混雜** | 帳號（登出／設定）、建立（上傳／TXT／空白／YouTube）、資料搬運（匯入／匯出 ZIP）平鋪在同一列，沒有分組 |
| D5 | **兩個搜尋入口** | 頂部「跨所有簡報搜尋」與篩選卡的「標題篩選」並存，使用者得先判斷該用哪一個 |
| D6 | **批次操作離選取目標很遠** | 勾選卡片後，操作 chips 出現在**篩選卡片底部**，而被選取的卡片在更下面 |
| D7 | **手機上破版** | 「上傳 PDF」擠成三行、「YouTube 匯入」文字**溢出按鈕邊界**；篩選卡片獨佔近一屏 |

D7 值得單獨說一句：`@mobile` 的橫向捲動測試是**通過**的（沒有溢出視窗），所以問題不在版面寬度，而在**每顆按鈕內部**被壓到無法閱讀。V2_PLAN P0-2 原本從「PlayPage 只有 2 處響應式 class」推測行動版會整個壞掉，實測顯示症狀其實是這種——這一節的論據應該據此修正。

## 2. 新架構：三層

把「這是什麼層級的動作」變成版面本身的結構，而不是靠顏色暗示。

```
① App bar（全域，永遠在）
┌──────────────────────────────────────────────────────────────────────────────┐
│ makeslide      [🔍 搜尋簡報、逐字稿、頁面文字…            ]              (👤▾) │
└──────────────────────────────────────────────────────────────────────────────┘
                                                                    └ 設定 / 匯入 ZIP
                                                                      / 匯出全部 ZIP
                                                                      / 登出

② Page toolbar（清單上方，sticky）
┌──────────────────────────────────────────────────────────────────────────────┐
│ [＋ 建立 ▾]   全部類別 ▾  ☆ 我的最愛      [🔍篩選標題]  標題 A-Z ▾   [▦|≡]  ⋯ │
│  └ 上傳 PDF                                                                   │
│    貼上 TXT                                                                   │
│    空白簡報                                                                   │
│    YouTube 匯入                                                               │
├──────────────────────────────────────────────────────────────────────────────┤
│ 4 份簡報 · 4 頁 · 播放 0 次                                                    │
└──────────────────────────────────────────────────────────────────────────────┘

③ Contextual bar（只在選取時取代 ②）
┌──────────────────────────────────────────────────────────────────────────────┐
│ ✕  已選 6 份    [加入我的最愛] [移至分類▾] [新增標籤▾] [生成合輯] [匯出]  [刪除] │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 2.1 每顆按鈕的去向

| 現在 | 去哪 | 為什麼 |
|---|---|---|
| 上傳 PDF | **建立** split button 的預設動作 | 最高頻的建立方式，維持一鍵可達 |
| 貼上 TXT／空白簡報／YouTube 匯入 | 建立選單內 | 全都是「建立一份新簡報」，只是來源不同——它們該是一個決定的四個選項，不是四個決定 |
| 匯入 ZIP | 帳號選單 | 一次性的搬遷動作，不是日常操作 |
| 匯出全部 ZIP | 帳號選單，加二次確認 | 罕用且重（打包整個帳號），不該在主視線內一鍵可觸 |
| 設定／登出 | 帳號選單（👤） | 業界慣例；也把頂部列的擁擠一次解決掉 |
| 標題篩選 | Page toolbar，改為即時篩選 | 與全域搜尋分工：**全域＝跨簡報找內容，篩選＝在看得到的清單裡縮小範圍** |
| 顯示類別／排序／視圖切換 | Page toolbar | 它們是「怎麼看這份清單」，本來就屬於清單，不該獨立成一張卡片 |
| ☆ 我的最愛／全選 | 我的最愛升為 toolbar 的篩選 chip；全選移入 ⋯ 溢位選單 | 我的最愛是常用的篩選，全選只在要批次操作時才需要 |
| 批次操作 chips | **Contextual bar** | 選取時才存在的動作，就該在選取時才出現，且緊貼清單上緣 |

### 2.2 三個設計原則

1. **一個主要動作**。整個頁面只有「建立」是 primary 樣式，其餘一律 secondary 或 ghost。目前 5 種樣式並存，等於沒有層級。
2. **罕用與破壞性收進選單**。判準是「誤觸的代價」：匯出全部 ZIP、刪除、登出都應該多一步。
3. **選取是一種模式**。進入選取後 toolbar 整條換成 contextual bar，而不是在既有版面塞更多 chips——後者正是現在批次操作離目標很遠的原因。

## 3. 實作步驟

刻意切成可獨立驗證的四批，每批都能單獨 merge，不必一次改完。

| 批次 | 內容 | 產出 |
|---|---|---|
| ~~**B1**~~ ✅ | 抽出可重用的 [`Menu`](../frontend/src/components/Menu.tsx) 元件，鍵盤巡覽邏輯抽成純函式 [`menuNavigation.ts`](../frontend/src/components/menuNavigation.ts) | 元件＋15 組純函式測試 |
| ~~**B2**~~ ✅ | 帳號選單：設定／匯入 ZIP／匯出全部 ZIP／登出移入 👤 | 頂部列剩下品牌＋搜尋＋建立按鈕＋👤 |
| ~~**B3**~~ ✅ | 建立 split button：上傳 PDF 為預設，其餘三種來源進選單（[`UploadButton`](../frontend/src/components/UploadButton.tsx)） | 建立入口收斂成一個 |
| ~~**B4**~~ ✅ | Page toolbar＋Contextual bar：篩選欄位壓成單列，批次操作抽成 [`HomeSelectionBar`](../frontend/src/components/HomeSelectionBar.tsx) | 選取時才出現的 sticky 操作列 |

無障礙不是額外項目：`Menu` 一開始就要有 `role="menu"`／`aria-expanded`／方向鍵巡覽。事後補的成本高得多，而全庫目前 174 個 `aria-*` 已經偏少。

### B1+B2 完成後的實測

- 頂部列從**兩列變一列**（header 高度 ~120px → ~70px），原本折行的四顆按鈕全部單行。
- 手機上「上傳 PDF」從三行變一行，「YouTube 匯入」的文字不再溢出邊界。
- 建立入口（四顆）在手機上仍佔兩列——這是 **B3 的工作**，split button 落地後會收成一顆。
- 把鍵盤巡覽抽成純函式立刻有回報：測試抓到 `ArrowUp` 在「尚未選定任何項目」時會落到**倒數第二項**而不是最後一項（`(-1-1+3)%3 = 1`）。這種 off-by-one 在畫面上只是「跳錯一格」，肉眼很難察覺。

### B3+B4 完成後的實測

- 頂部列剩下 **品牌＋搜尋＋一顆建立 split button＋👤**。手機上建立入口從四顆兩列收成一顆。
- 篩選區從「三個直式 label+select 的卡片」壓成單列；手機上從獨佔近一屏縮到兩列，**第一張卡片進入首屏**。
- 批次操作改為 sticky 的 [`HomeSelectionBar`](../frontend/src/components/HomeSelectionBar.tsx)，緊貼清單上緣，選取與操作在同一個視野裡。它帶 `role="toolbar"`＋`aria-live`，因此輔助技術會知道進入了選取模式。
- 一條既有 E2E 如預期地紅了：「從首頁建立空白簡報」原本點的是頂部列的按鈕，而該按鈕現在在下拉裡。這是**刻意的改變**，已由「從建立下拉可以做出一份空白簡報」取代——規劃裡說的「改版後若紅了，值得檢查而不是直接改測試」在這裡確實派上用場。

## 4. 驗收

用既有的 E2E harness，每一批都可以量：

- **不折行**：1440px 下 toolbar 內每顆按鈕的 `clientHeight` 不超過單行高度（現在有 4 顆是兩行）。
- **手機不破字**：390px 下按鈕文字不溢出邊界（`scrollWidth <= clientWidth`，逐顆檢查——現在「YouTube 匯入」不合格）。
- **主要動作唯一**：primary 樣式的按鈕在頁面上只有 1 個。
- **選取模式**：選取後 contextual bar 出現且批次動作可用，取消後回到原 toolbar。
- **鍵盤可達**：Tab 進入選單、方向鍵移動、Esc 關閉並把焦點還給觸發按鈕。
- **既有 35 條 E2E 全綠**：這次改的是版面，功能行為不該變。首頁那幾條測試用的是 `getByTitle`／`getByRole`，改版後若紅了，代表可及名稱真的變了，值得檢查而不是直接改測試。

## 5. 不做的事

- **不改卡片本身**。這次只動清單上方，卡片的資訊密度是另一個題目。
- **不引入 UI 元件庫**。只缺一個 `Menu`，為它加一整套依賴不划算，而且 Tailwind 的樣式慣例已經一致。
- **不做指令面板（⌘K）**。在功能表區收斂之前就加一條平行入口，只會讓「同一件事有兩個地方可以做」的問題更嚴重。這件事適合等 B1–B4 落地後再談。

# 測驗功能的踩坑記錄——AI 寫的程式，一樣會犯沒想到的錯

這份文件回顧 MakeSlide 的「線上測驗」從無到有的半年，把真正踩到的坑攤開來看。寫它的動機不是檢討，而是回答一個常被問到的問題：**讓 AI 寫程式，是不是就不會有那些「人才會犯」的錯？**

答案是不會。下面每一個坑都是真的發生過、有 commit 可查；一部分是自己回頭審視時找到的，但**最痛的幾個都是在真實課堂上被學生或老師撞到**才發現的。AI 寫程式的速度快，所以坑也累積得快；犯錯的種類跟人高度重疊。

資料來源：這個 repo 的 commit log（`git log --grep=quiz`）、`TODO.md` 的工作記錄（每一條都留有當時查到的根因），以及出事當天的伺服器日誌與資料庫。

- **9 月**：身分問題（學號）、Markdown 與公式、問答題拍照作答、防弊改成可關閉、小考分析。
- **10–11 月**：介面語言、選項顯示、以及最嚴重的一次——**學生離開後回不到測驗中**。

## 二、踩過的坑，依性質分類

### 1. 「信任客戶端」

分數原本是前端算完、連同作答一起送上來存。也就是說，任何學生只要會改 HTTP 請求，就能給自己 100 分。

- `fix: compute quiz attempt scores server-side instead of trusting the client`（6/20）
- 同一週還補了十幾個端點的權限檢查：測驗的寫入、讀取、刪除、重新生成、版本還原、投票……全都原本沒有檢查呼叫者是誰。

**為什麼沒先想到**：功能是從「老師自己用」的情境長出來的。一旦同一個頁面開始給學生用，每一個端點的信任邊界都變了，但程式沒有跟著重新審視。這是人類團隊最典型的技術債累積方式，AI 一模一樣。

### 2. 資料結構的隱性契約

同一份資料結構被多個功能共用，每個功能對它都有「沒寫下來的假設」。

- **問答題存不下來**（7/18）。編輯器所有題型共用同一份結構，切換成「問答題」時只改了題型，沒清掉原本那 4 個空選項，後端驗證「選項文字至少 1 字」就擋下來。同時存檔的正規化流程要求「至少 2 個選項」，問答題根本過不了。
- **AI 改題回 500**（7/18）。提示詞叫模型「新增題目時 id 留空」，模型就回傳 `id: ""`；但驗證規則是 `.min(1).optional()`——`optional` 只放行「沒有這個欄位」，不放行空字串。
- **沒設學號的學生，作答從來沒有被記錄**（9/15）。前端沒學號時送 `code: null`，後端的 `optional` 同樣不吃 `null`，回 400；而前端把這個錯誤靜默吞掉了，畫面上什麼都沒顯示。**資料庫裡 123 筆作答全部都有學號，所以這個 bug 存在了很久都沒人發現**——有設學號的人一切正常。那位學生的作答已經永久救不回來。

**為什麼沒先想到**：`null` 和 `undefined` 的差別、`optional` 的語意，這些都是「寫的時候知道、用的時候忘記」的細節。更關鍵的是第三個例子裡的設計決定：**把錯誤吞掉**。那一行 `.catch(() => {})` 寫下來的時候看起來只是「不要讓錯誤弄壞畫面」，實際效果是「讓資料永久消失而且沒人知道」。

### 3. 同一個欄位被兩個功能借用

同步協定裡有一個欄位叫 `active_quiz_id`。測驗功能用它表示「正在進行的測驗」；而即時投票功能也用它，表示「正在顯示的投票」（通常是 null）。

結果：老師同時開著投影頁和測驗頁時，兩個分頁會互相搶同步主控權，投影頁的心跳就把 `active_quiz_id` 推成 null——**整場測驗被清掉，全班被強制交卷**。`quiz_show_answers` 同樣被借去當「是否公布投票結果」。

這個坑從 5 月埋到 11 月才被挖出來，因為它只在「老師兩個分頁同時開著」時才發作。

**為什麼沒先想到**：借用現成欄位比新增欄位省事，而且當下兩個功能不會同時用。「不會同時用」是一個沒有被寫下來、也沒有任何程式在維護的假設。

### 4. 狀態的生命週期沒人負責

這一類坑最多，而且最難查。系統裡有一堆各自獨立的「有效期」：

| 狀態 | 期限 | 踩到的坑 |
|---|---|---|
| 老師的同步主控權 | 10 分鐘 | 到期就把整場測驗拆掉（見下） |
| 學生的連線 | 30 秒 | 到期就把學生從老師的名單上刪掉，老師再也看不到他、也無法讓他重新進入（7/13 修） |
| 測驗場次 id | 只存在記憶體 | 後端一重啟就變 null，每個學生的「場次鍵」退化成同一個值，跟以前的紀錄撞鍵，一進來就顯示「你已完成作答」（11/02 修） |
| 學生端的鎖定旗標 | 永久 | 沒有過期、沒有自救路徑，只能等老師按「允許重新進入」 |

**11 月 2 日那次最嚴重，值得完整說**：老師把分頁切到另一份簡報去開第二份測驗，原本那份簡報的主控權在 10 分鐘後到期，伺服器就執行「重置同步模式」——把測驗模式、進行中的測驗、場次 id、全班的作答進度**一次全部清空**。後果是：

1. 還在作答的學生被強制交卷。有些人交出的是空白卷，而多選題對「正確地沒有勾選」也給部分分，所以**空白卷還拿到 25 分**，在成績單上看起來就像一次真的低分作答。
2. 想重新進入的學生一律被擋（那天光這一個錯誤就回了 **387 次**）。
3. 老師的「測驗中的學員」名單變空，連「允許重新進入」都按不到人。

而老師那邊完全看不出有問題，因為老師自己的頁面一切正常。最後老師只能另外開一份一樣的測驗，給那四個進不去的學生補考。

這個 bug 的定位靠的不是讀程式，是**翻伺服器日誌**：把那天所有失敗請求按分鐘分布畫出來，發現失敗的尖峰正好在「老師最後一次推送狀態 + 10 分鐘」那一刻。

**為什麼沒先想到**：「主控權到期就重置」在單純的播放同步情境下完全合理——老師走了，就不要讓學生繼續跟著一個不存在的人。但「正在考試」是一個完全不同的情境：**老師暫時離開，考試並沒有結束**。寫那段重置邏輯的時候，測驗功能還不存在。

### 5. 模型本身的偏差，不是提示詞的問題

- **答案幾乎都是 A**（8/03）。語言模型寫選擇題時，正確答案落在第一個選項的機率遠高於隨機。叫模型「請隨機排列」不可靠，最後是**存檔前自己用 Fisher-Yates 重排**，並把正解索引跟著映射過去。這裡還埋了一個陷阱：出題 API 回傳的選項順序必須是重排後的，否則學生選對了也會被判錯。
- **模型整題不寫題幹**（9/18）。提示詞把每個欄位都描述了，唯獨沒說題目本文要放在 `question` 欄位，模型就把那串當成完整規格、整題不寫題幹。查日誌發現這個失敗從 8/16 以來 14 次呼叫中出現了 7 次，兩種模型都會中。
- **重試等於再失敗一次**。原本的重試只是把 token 上限調高、把同一份請求再送一遍，模型當然重複同樣的遺漏。改成把上一次的輸出和具體的驗證錯誤一起回饋給模型，才真的救得回來。
- **模型傾向自己決定沒講清楚的事**（11/01）。單題 AI 改題的提示詞允許「2 到 8 個選項」，模型就常常回 6 個。改成「除非老師指定，否則一律 5 個」。

**為什麼沒先想到**：寫提示詞的時候，自己腦中已經有完整的資料結構，很容易以為「這還需要說嗎」。模型沒有那個腦中的結構，它只有你寫下來的字。

### 6. 真實使用環境和開發環境是兩回事

監考功能特別吃這一類坑，因為它依賴瀏覽器的行為：

- 手機切到背景時 JavaScript 會被**凍結**，計時器不會跑。所以「離開 10 秒才算違規」不能只靠計時器，必須在回來時用時鐘時間差補判。
- 桌機分頁被背景時會被**節流**，而「切走」正是要偵測的違規情境本身。
- 螢幕自動休眠會讓頁面被判定為隱藏，誤觸違規——所以加了螢幕常亮鎖。
- 學生按 ESC 離開全螢幕之後，原本「自動把學生拉回測驗頁」的邏輯整段失效，而畫面上沒有任何手動入口可以按。
- 學生關掉分頁再開，連線 id 就換一個（它存在 sessionStorage），老師按的「允許重新進入」對準的是舊的 id，**永遠打不到那個學生**。
- 老師同時開兩個分頁（投影＋控制），兩邊互相搶主控權。

**為什麼沒先想到**：開發時是在一台桌機、一個分頁、網路穩定、不會休眠的環境下測的。教室裡是 30 台不同的裝置、手機、平板、會鎖屏、會斷線、會被切走。

### 7. 「以懷疑為前提」的設計特別容易傷到無辜

防弊是整個功能裡最反覆的一塊：

1. 先做「離開就記違規，兩次自動交卷並鎖定」。
2. 使用者要求「10 秒內回來不算」——改成離開／返回的寬限模型，並在畫面上顯示倒數（原本是 10 秒後突然跳警告，學生根本不知道發生什麼事）。
3. 鎖定之後學生只能等老師解鎖，而老師那邊的狀態還會被學生頁面的自動回報「翻回作答中」，導致解鎖按鈕消失——**死結**（7/13 修）。
4. 最後使用者的結論是：**誤判太多，請讓它可以完全關閉**（9/22）。關閉後離開只警告、隨時可以回來，但每次離開的時間與長度都記錄下來給老師看。

這一塊的教訓是：一個「抓作弊」的機制，它的錯誤代價是不對稱的。抓不到作弊只是少抓一個；誤判一個認真作答的學生，是直接讓他考不完。而最常觸發它的，往往不是作弊，是手機跳出通知、螢幕休眠、網路斷一下。

### 8. 看得見的小事也會完全擋住人

- 「進入測驗」按鈕在淺色模式下的文字對比只有 **1.04:1**（幾乎看不見）。
- 唯讀身分的學生，header 上的測驗入口被套用了「生成功能」的停用樣式，**根本點不進去**；而另一條自動導航的路只在全螢幕模式才成立，所以非全螢幕的學生兩條路都不通。
- 選項太長時不換行，只能左右捲動才讀得完（7/19 修了作答端，11/01 才發現編輯端也一樣）。
- 監考規則的標題和按鈕有翻譯，但規則本文是從 markdown 檔讀的，只有中文版——英文介面的學生看到一整頁中文規則。
- 一題都沒答的空白卷會被記錄下來，而且因為部分分機制還有分數。

### 9. 根本不是程式的坑

- **11/01 使用者回報「選項還是沒換行」。程式早就改好了**，但建置程序在合併時的分支切換瞬間建出了舊版，之後沒再重建，網站一直送舊的前端。無程式變更，重建就好。
- 同步到另一台機器時，後端的檔案監看沒偵測到變更，必須手動碰一下進入點才會重啟——所以「改好了卻沒生效」出現過不只一次。
- 要查的簡報和資料庫在另一台機器上，本機查不到。

這一類坑的共同點是：**症狀和原因之間沒有因果關係**。回報的人說「這個 bug 沒修好」，程式碼裡看起來明明修好了，兩邊都沒說錯。

### 10. 測試會把錯的行為釘住

- 打亂選項之後，原本的測試開始失敗——因為它寫死了「正解是索引 0」。那個假設在測試裡存在很久，而且它本來就不該成立（真實客戶端只能用選項內容去找）。
- 9 月為了「解析完整顯示」寫的自動長高輸入框，11 月被拿去用在選項上時才發現：**它從來沒有把列數傳給底層元件**，所以瀏覽器一律以預設的兩列計算，最小一列的設定從來沒生效過。寫的時候有測試、有型別檢查，都沒抓到。

## 三、AI 犯的錯和人犯的錯，差在哪裡

**一樣的部分（這是重點）**

- 看不見跨檔案、跨功能的隱性契約。`active_quiz_id` 被兩個功能借用、`optional` 不吃 `null`、重置邏輯不知道後來多了考試情境——這些都是「每一處單獨看都合理」的錯。
- 對真實使用情境想像不足。開發環境永遠比教室乾淨。
- 對剛寫好的程式過度自信。TODO 裡反覆出現一句話：「未做實機驗證」。
- 把使用者的話當規格照做，而不是先問「那如果老師中途離開會怎樣」。

**AI 比較容易的**

- **產出速度快，所以坑累積得快。** 六月一個月 185 個相關 commit，等於一個月內鋪下了之後半年要踩的地雷。人類團隊會被自己的速度限制住，AI 不會，所以必須靠別的機制（測試、日誌、文件）補上那個天然的煞車。
- **沒有「被咬過」的肌肉記憶。** 人踩過一次 `null` 的坑，下次會多看一眼；AI 每一次對話都是新的，除非把記憶**外化**成測試、文件、或 `TODO.md` 裡的工作記錄。這個 repo 之所以查得出 11 月那個 bug 的來龍去脈，就是因為前面每一次修正都留下了「根因」。
- **文件寫得漂亮，但不等於驗證過。** 一份結構完整、理由充分的修正說明，和「真的在教室裡跑過」是兩件事，而前者很容易被誤認為後者。

**人比較容易的**

- 懶得寫測試、懶得寫文件、懶得查根因就直接改。這部分 AI 反而穩定得多——55 個修正裡，大多都附了根因說明與對應的測試。

## 四、真正有效的做法

從這半年回頭看，有幾件事是明確有效的：

1. **先找根因，再改程式。** `TODO.md` 裡每一條修正都有「根因」一段。它的價值不只在當下——11 月那次能排除「防弊誤鎖」這個最像兇手的嫌疑犯，靠的就是前面留下的脈絡。
2. **日誌和資料庫是最可靠的證人。** 11 月那次完全是靠伺服器日誌的失敗時間分布，和資料庫裡「同一個學號兩筆作答、一筆 10/10、一筆 0/10」這種痕跡定位的。讀程式只能產生假設，日誌才能證明。
3. **把限制寫進環境，而不是寫成規則。** 兩個對照：擋作弊的字串黑名單擋不住 `window['fet'+'ch']`，但瀏覽器的內容安全政策擋得住；叫老師「記得別切分頁」沒有用，讓「測驗進行中就允許學生重新加入」才有用。
4. **純邏輯抽出來，單獨測。** 寬限判定、計分、作答統計、作答草稿都是不碰 React 的純函式，所以每一條邊界（9999 毫秒不算、10000 毫秒算、空白卷怎麼判、壞資料怎麼處理）都可以直接測。
5. **接線也要釘住，但要檢查釘的是不是對的行為。** 沒有渲染測試環境時，用原始碼層級的守門測試釘住關鍵接線是有效的；但「答案是索引 0」那個例子提醒我們，測試釘住的可能是錯的假設。
6. **錯誤不要吞掉。** 整份記錄裡代價最高的一行程式，就是那個把上傳失敗靜默忽略的 `.catch`。

## 五、一句話總結

AI 可以在半年內寫出 374 個 commit 的功能，但它和人一樣**看不到自己沒想到的東西**——而「沒想到的東西」幾乎全部來自真實世界：老師會切分頁、手機會凍結、學生沒填學號、網路會斷、前端會忘記重建。

所以真正的差別不在「誰寫程式」，而在**有沒有把真實世界的回饋接回來**：使用者的回報、伺服器的日誌、資料庫裡的痕跡，以及每一次修正留下的根因記錄。

這份文件本身就是那套機制的一部分。
